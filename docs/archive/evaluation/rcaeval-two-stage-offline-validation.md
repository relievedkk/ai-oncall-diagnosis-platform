# RCAEval 两阶段协议 v3：边界加固与验证记录

> 历史材料：当前操作入口见[评测导航](../../evaluation/README.md)。正文中的版本和状态仅适用于当时。

验证范围：两阶段离线流程、边界加固及18例开发集运行。

## 验证结论

- 54/54 案例遥测可读、初始证据包可构建，且同一案例连续构建两次的正文与 SHA-256 完全一致。
- 54/54 证据包通过实际 `sanitize_tool_message` 边界，没有 `tool_result_truncated` 或失败预览。
- 模型调用为 0，协调器接收案例列表为空；剩余 36 个案例未传入任何模型协调器，也未读取其答案。
- `validate` 模式不会把 `--answers-file` 交给 54 例 `Pilot`，遥测自检不依赖密封答案；候选召回只在证据包完成后，通过独立的 18 例开发集真值加载器计算。
- 当前工具结果上限为 16 KiB，包体 min/P50/P95/max 为 9,354 / 13,954 / 14,913 / 14,999 bytes。live runner 与离线门禁使用同一配置上限。
- 18 例开发集初始候选召回 18/18；“初始候选或 hint”召回同为 18/18。该指标只说明答案服务在证据边界内可见，不代表模型能正确判断根因或故障类型。
- 开发集包体 min/avg/max 为 10,103 / 12,920.3 / 14,977 bytes；平均 2.56 个初始候选、4.61 个 hints。

## 协议变化

协议 v3 为 `single_stage` 与 `agent` 只构建一次不可变初始包，并向两边传入字节和哈希完全相同的副本。`baseline` 只作为显式旧别名映射到 `single_stage`，新旧实验不得静默合并。

Agent 第一轮只生成扁平、严格校验的 `RouteDecision`，选择直接进入诊断或提交结构化 `EvidenceRequest`；无论是否补查，第二次模型调用才生成 `DiagnosisResult`。合法请求最多增加一个已有 hint 和目录依据的服务，并只返回一种视图与请求的机理；第二轮不能继续补查。Ground truth 在两边结果冻结后才加载。

评分 v3 分开报告端到端准确率、执行成功条件准确率、初始/补查后候选召回、安全 unknown、失败类别和模型用量。安全拒答不再与 provider、超时或依赖失败混为一种“错误”。

协调器使用闭集失败分类，分别记录 timeout、provider setup/provider、无效模型输出、无效补查请求、补查 loader 和策略门禁失败。每条 v3 记录还保存来自实际初始/已验证补查包的有效 evidence ref 清单，引用有效性不再依赖缺失的旧版 `evidence` 数组。

每种策略使用一个单调时钟总截止时间，模型调用、补查和策略门禁共享剩余预算；同步补查 loader 与同步 policy 使用独立、并发有界的执行器，不占用 asyncio 默认 executor，也不能阻塞事件循环导致整对结果无法落盘。超时 loader 不再修改 runner 共享字典，已验证 follow-up refs 由协调器结果显式返回。补查包在第二次模型调用前会校验 schema、case、原始 request、候选服务、机制 key/profile 一致性、fact 的服务/机制/ref 双向绑定与唯一所有权，以及 logs/metrics/traces/topology 的视图范围。

## 16 KiB 边界处理

候选数由实际字节预算自适应从 5 向下收缩。超限时先删除日志、Trace 与趋势摘录，再压缩文本及低优先级 hint 邻接/引用；必要时只保留最高优先级 hints。每个语义裁剪都记录在 `omitted_paths`。候选身份、直接机理状态、稳定引用和拓扑方向不以截断预览代替。

候选画像中的 unavailable 计数为：CPU 0、mem 0、delay 38、disk 26、loss 128、socket 0。计数单位是“已入选候选画像”，不是案例数；loss 大量 unavailable 符合当前数据缺少结构化网络 loss/drop/retransmit 字段的事实，不能由日志关键词补齐。

## 已知限制

- common-mode 采用“至少三个且严格超过服务目录一半的服务，在一个 60 秒桶内同时出现直接信号”的确定性启发式；它降低大目录中 3 个局部异常被误判为公共噪声的风险，但仍可能低估真实多服务共同故障。
- 候选召回已达 18/18，但故障机理仍可能不可辨识；多个直接机理同时出现时应输出 `unknown`，不能跨单位比较倍数后猜测。
- 54 例离线门禁验证的是证据、安全和执行协议，不是模型准确率。历史协议 v2 的准确率不能与未来 v3 结果直接合并。
- 剩余 36 例仍保持 sealed/unrun；本轮没有运行模型或进行最终盲测。

## 边界加固复验

加固后的 54 例无模型门禁产物为 `.runtime/rcaeval/<experiment>/validation.json`。门禁通过，模型调用为 0，协调器案例为 0，18 例开发集初始及“初始或 hint”候选召回均为 18/18，剩余 36 例保持 sealed/unrun；包体最大 14,999 bytes。

边界加固还完成了以下协议检查：跨阶段完全相同的 evidence identity 会去重，真实身份冲突仍会被拒绝；协调器和补查构建器共用同一授权器；失败使用固定类别与 detail code；产物显式保存可空的 `route_action` 和 `evidence_request`，但不保存原始模型响应、provider exception 或遥测正文。

聚焦测试和完整测试套件均通过。任务相关文件通过 Ruff check、Ruff format check 与 `git diff --check`。全仓库 Ruff 仍有既存的 7 个 lint 问题和 72 个待格式化文件，均位于本任务以外，未在本次修改中顺带改写。

## 18 例开发集实跑结果

新产物目录为 `.runtime/rcaeval/<experiment>/`，没有覆盖旧结果。两种策略的端到端结果如下：

| 指标 | single_stage | agent |
| --- | ---: | ---: |
| 执行成功率 | 18/18（100%） | 7/18（38.9%） |
| 服务命中率 | 6/18（33.3%） | 3/18（16.7%） |
| 故障类型命中率 | 2/18（11.1%） | 2/18（11.1%） |
| 联合命中率 | 2/18（11.1%） | 2/18（11.1%） |
| 成功执行条件下服务命中率 | 6/18（33.3%） | 3/7（42.9%） |
| 成功执行条件下联合命中率 | 2/18（11.1%） | 2/7（28.6%） |
| 安全 unknown 率 | 14/18（77.8%） | 5/18（27.8%） |
| 模型调用数 | 18 | 26 |
| provider 观测 tokens | 128,563 | 180,054 |

Agent 的 11 个失败中，9 个是首轮 `RouteDecision` 未通过严格结构校验，1 个是合法补查后的 `DiagnosisResult` 未通过结构校验，1 个是请求扩展未获初始证据包授权。没有超时、预算耗尽或 `provider_error`。每个 Agent 案例最多两次调用，全部调用都有完整 provider usage；每个失败都有固定 category、detail code 以及显式可空的请求/动作审计字段。没有再次出现适配器制造的重复 evidence identity 冲突。

与上一轮相比，Agent tokens 从 234,418 降至 180,054，服务命中从 0/18 提升至 3/18、联合命中从 0/18 提升至 2/18；但执行成功率从 10/18 降至 7/18。说明边界安全和失败归因已经稳定，模型对严格路由 schema 的服从度仍不足，当前 Agent 尚不能替代 single-stage 基线。

由于安全约束有意不落盘原始模型响应，本轮只能确定 9 例在 `RouteDecision` Pydantic 边界失败，无法从产物追溯到具体缺失或多余字段。这是下一轮改进的可观测性限制：若要继续优化，应增加不含字段值和原文的安全校验摘要（例如固定的 schema issue code/字段路径），先区分 action 契约、缺字段、额外字段和枚举错误，再决定调整提示词或供应商结构化输出适配；不应放宽 `extra="forbid"` 或清洗后接受无效输出。

本结果只覆盖已反复用于开发的 18 例，不能作为最终泛化精度。剩余 36 例仍未调用模型；在路由执行成功率得到改善并冻结实现前，不应消耗这部分盲测集。
