# 安全与异常边界复查修复（2026-10-23）

本次在前一轮六项修复后继续审查上传、检索、鉴权和诊断流。保留工作区原有修改，没有提交或推送代码。

## 新发现并修复的问题

1. **上传锁连接丢失后恢复清单可能覆盖后来的成功请求。** 文档锁、集合写锁和版本指针现在共用一个 PostgreSQL 连接及外层事务；嵌套锁不会提前提交。每次上传写入独有 attempt，失败后重新获取文档锁，只有清单仍属于本次请求时才恢复旧清单。另一请求即使上传相同内容也不会被误回滚。
2. **外层提交异常被误报为普通失败，旧向量可能提前清理。** 上传和目录重建在真正提交确认后才清理旧向量；提交响应丢失时保留可协调的数据，上传返回 503 和 `pending_reconciliation`。如果清单恢复时无法重新取锁，也报告需要协调。
3. **新版本已提交，但不同客户端仍可能读到 Milvus 旧快照。** ANN 检索显式使用 Strong 一致性，避免新 PostgreSQL 指针过滤旧快照后误报无资料。
4. **目录白名单没有覆盖文件链接的最终路径。** 普通文档、catalog 文件和 catalog 指向对象都校验解析后的路径范围；上传清单目录和文件也校验范围。拒绝指向选定目录外的文件与清单。
5. **非 ASCII 鉴权字段触发 500。** API Key、Webhook、会话 CSRF、退出登录及 CLS Token 验证统一将文本编码为 bytes 后做常量时间比较；非法凭据正常返回 401/403。
6. **诊断前台和后台重试生命周期不一致，前端还会吞掉部分终态错误。** Celery 管理重试时 Runner 保留非终态，由队列策略决定 retrying 或 dead_lettered；SSE 将单次尝试错误作为进度，只有数据库确认终态才发 complete/error。无错误证据的终态失败仍会发 error。前端只捕获 JSON 解析错误，正常上报英文等终态错误；连接意外结束不再算作成功。

## 仍然存在的边界

PostgreSQL、Milvus 与磁盘文件之间仍然没有跨系统原子事务。进程崩溃或提交结果不确定时，应通过 uploads 根目录重建选定版本；503 表示需要协调，不表示已撤销。孤立分片通过共享版本记录过滤，长期仍需制定保留和整理策略。

诊断流本次修复的是重试与终态语义，没有新增断线自动重连、取消任务或任务创建幂等键。断开浏览器不会取消已入队的任务。原审查中的任务历史分页、上下文/成本预算和语义质量评测仍属于后续改进范围。

Windows 当前令牌不能创建真实文件软链接，目录逃逸回归通过模拟解析后的外部目标验证；尚未执行 Linux 文件系统上的实体软链接端到端测试。真实依赖测试仍有现有 PyMilvus ORM API 弃用警告。
