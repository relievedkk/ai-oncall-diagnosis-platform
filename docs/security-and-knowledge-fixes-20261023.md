# 六项安全与知识库修复（2026-10-23）

本轮对应审查报告第 1–6 项。保留工作区原有修改，新增回归测试后逐项修复，并更新本地运行中的 API、CLS 网关和诊断容器。

后续复查补修了上传锁丢失、外层提交、Strong 检索、文件链接范围、非 ASCII 凭据和诊断重试/终态问题，详见 [复查修复记录](review-followup-20261023.md)。该记录包含最新验证数量与仍然存在的边界。

## 修复结果

1. **CLS 入口认证**：官方 `cls-mcp-server@1.2.1` 改为私有 stdio 子进程，认证网关负责 HTTP；客户端必须使用独立 `MCP_CLS_TOKEN`。本地启动自动生成密钥，Compose 传给诊断 Worker，未认证请求返回 401。旧的裸 HTTP 服务会被启动脚本拒绝沿用。第三方启动日志通过 Node preload 转到 stderr，不污染协议 stdout。
2. **慢请求与执行许可**：先验证身份，再在总期限内读取请求体，最后进入聊天执行许可；默认总读取期限 15 秒，可通过 `REQUEST_BODY_TIMEOUT_SECONDS` 调整。超时返回 408 并关闭连接；请求字节上限继续生效。
3. **API 运行期限**：移除本地原生进程的累计 10,000 请求退出条件，保留明确关闭和并发限制。这不等于增加了任意崩溃后的自动恢复能力。
4. **来源限流**：不再使用尚未验证的 X-API-Key/Bearer 文本作为分桶身份，轮换垃圾请求头无法获得新的登录来源配额。账号锁定仍独立生效。当前限流仍是进程内、按直接连接 IP；共享网关场景需要另行配置可信代理和共享配额。
5. **文档身份与版本**：在共享知识库内，以规范化原文件名确定稳定文档 ID，内容哈希表示版本；保留原文件名和版本元数据。同名更新替换旧索引，同内容不同文件名保持独立身份。不可变文件保存在 `uploads/.objects`，当前版本清单保存在 `uploads/.documents`。目录重建只重建清单选定版本，不允许直接索引内部存储目录。
6. **读写并发与错误语义**：远程向量化移到集合写锁外；读操作使用 PostgreSQL 共享 advisory lock，写操作使用同键排他锁。检索失败抛出明确异常，知识工具不再将依赖故障描述为没有资料。

## 版本提交与故障恢复

迁移 `20261023_0009` 新增 `knowledge_document_versions`，它是 API 和 Worker 共同使用的可检索版本记录。新向量持久化后才提交版本指针，指针提交确认后再清理旧向量；清理失败不会撤销已经提交的新版本。读端过滤旧版本和未提交的受管理分片，因此 Milvus 残留不会直接成为检索依据。

协调事务提交结果不确定时，系统保留新文件清单和两版向量，上传返回 HTTP 503、`index_status=pending_reconciliation`。可以通过索引 uploads 根目录重建选定版本，不会因为异常而静默切回旧内容。已确认的写入前失败仍保留旧清单与旧索引。

升级时执行：

```powershell
.\.venv\Scripts\python.exe -m app.local_env
.\.venv\Scripts\python.exe -m alembic upgrade head
```

随后停止旧 CLS HTTP 进程，启动 `python -m mcp_servers.cls_gateway`，重启 API 和诊断 Worker。当前工作区对应的运行实例已经完成此升级。备份时应同时保留 uploads 的对象与清单、PostgreSQL 版本记录以及 Milvus 数据。

## 历史数据的处理边界

旧实现已经将部分原始文件名丢弃，仅留下 32 位内容哈希文件名，无法可靠推断它们各自属于哪份业务文档。新查询会隔离这类缺少文档身份的历史上传向量，防止旧操作手册混入新版本；磁盘原文件和旧向量均未自动删除。

需要继续使用这些资料时，请确认对应业务文件名后重新上传。也可以从保留的旧文件内容中恢复资料，以明确的业务文件名上传。不要直接索引 `.objects` 或 `.documents`，也不要将跳过历史对象扫描等同于已恢复其原始身份。
