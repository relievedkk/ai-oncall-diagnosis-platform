# 诊断结果、案例评测、对照实验与无凭据演示设计

日期：2026-10-26（Asia/Shanghai）

状态：2026-10-26 用户在聊天中确认设计并授权实施及仔细测试。

## 目标与范围

用户已同意改进四项：结构化诊断结果与状态、可核验故障案例、固定流程对照、无真实凭据重放。用途为求职个人项目：让诊断结论、方案收益和演示过程可以检查，而非扩展为企业高可用系统。

沿用 Python、FastAPI、LangGraph、PostgreSQL、现有持久任务与 SSE；真实处置继续仅 Dry Run。本次不引入新模型供应商、额外 Agent、多租户或生产写权限，不重写主前端。

## 已检查的现状

- `PlanExecuteState.response` 与 Replanner 的 `Response.response` 为字符串；报告和完成事件保存 Markdown。
- Runner 的 `completed` 表示任务执行完成，不直接表示根因已确认；重试、死信、所有权与预算机制已经存在。
- 工具证据在 Executor 中收集，再由 repository 分配持久事件/证据 ID。结构化引用必须有生成前即可得到、重试后仍可解释的身份，不能要求模型预测数据库自增 ID。
- `DiagnosisReport` 当前只保存正文；内存仓储和 SQL 仓储都需要兼容新增字段；流式终态既可能来自持久事件，也可能由数据库摘要重建。
- 现有评测是 5 个案例的关键词/证据门禁，明确没有验证语义准确率，须保持旧 CLI 和口径兼容。
- 主应用的模块导入依赖非空模型配置；独立重放入口不能导入整套应用初始化并要求 Docker 或云密钥。

## 方案与取舍

1. 兼容扩展：增加类型化诊断结果，由校验后的结构生成 Markdown，复用当前持久化、队列和 SSE。改动可分步验收，旧历史可继续读取。**采用此方案，符合前一轮已同意的兼容改进方向。**
2. 重做诊断 API 和主界面：结构更自由，但会扩大认证、历史兼容和重连的改动面，不适合本次求职改进。
3. 仅添加样例报告和演示页面：实施较少，但不能改善真实 Agent 的结论约束，不满足本次授权范围。

具体字段、首批案例数和演示端口为实现方提案，不视为用户逐项指定。

## 一、结构化诊断结果

增加独立报告契约模块，避免模型/数据库初始化副作用。结果采用 `schema_version=1`，至少包含：

- `outcome`：`diagnosed`、`insufficient_evidence`、`budget_exhausted`、`dependency_failed`、`no_active_alerts`、`legacy_unverified`。
- `summary`：范围受限的总结。
- `observations`：观测事实列表，每项为正文和 `evidence_refs`。
- `hypotheses`：候选原因列表，每项含描述、支持引用、反证引用及 `supported/unverified/rejected` 状态。
- `missing_evidence`：未取得的必要证据。
- `next_checks`：可以执行的后续验证建议。
- `limitations`：依赖失败、截断或未覆盖范围。
- `validation_issues`：由程序产生的校验问题，不能由模型自行宣告通过。
- `termination_reason`：由工作流/Runner 设置，模型不能覆盖预算、超时和失败事实。

所有字段有字符串长度和列表数量上限；模型内容经过现有脱敏边界。`diagnosed` 只表示模型提出了带有效支持引用的诊断，不表示因果已被程序证明；界面使用“诊断结论（待人工复核）”。不新增无依据的百分比置信度。

### 证据引用

新增工具证据的稳定 `evidence_ref`。实现方采用随机 UUID，在首次采集工具结果时创建，随 evidence 写入检查点和持久化 payload；引用不是数据库自增 ID，也不能作为权限凭证。

生成报告前，按当前任务检查点中的证据建立只读引用表，包含 ref、类型、服务范围、成功状态、可用性及有界正文。报告只允许引用这个表内的 ID。重试恢复复用已保存 ref，新采集结果产生新 ref；同一 UUID 内容冲突视为无效。旧检查点缺少 ref 时，由任务上下文和证据序号派生兼容身份，前缀明确为 legacy，不补造证据。

校验至少检查：引用存在且属于本任务、重复 ID 无冲突、支持引用不是失败/示例数据、已知服务归属与本次目标不冲突。知识手册可支持假设，不能单独授权 `diagnosed`；缺少服务信息的证据不补猜服务归属。反证引用不因其与假设不一致而删除。

校验失败时，保留可追踪的警告与有效证据，不把无效引用呈现为有效支持；清除处置提案，避免诊断校验失败仍触发处置。正常结束的模型诊断降为 `insufficient_evidence`；已有权威预算/依赖失败结果保持原 outcome，引用错误进入 `validation_issues`，不得抹去失败原因。引用合法与语义正确分开评价。

运行上下文由执行器设定为 `production`、`replay` 或 `evaluation`，不能由模型指定。生产工具降级返回的 `demo/example` 数据在所有模式下均不能支持确认结论。受控合成实验中的有效观测使用独立 `synthetic_fixture` 来源，只在显式 replay/evaluation 上下文允许参与案例结论，并强制显示合成来源；production 不接受该来源。两种非生产上下文均关闭处置提案提交入口，不能仅凭 provenance 字段绕过真实处置证据检查。

### 工作流结果与执行状态

保持原有队列状态、重试和终态规则，新增的诊断 `outcome` 不替换 `job.status`。例如任务完成且诊断证据不足，可为 `job.status=completed/outcome=insufficient_evidence`。

- 触发步骤/模型调用/输入字节预算：`budget_exhausted`，保留有界证据和未执行步骤，不能宣称已完成诊断。
- 依赖或最终报告生成失败：`dependency_failed`；沿用已有重试策略，不因生成了部分报告而吞掉异常。
- 没有活跃告警：`no_active_alerts`，保留现有确定性报告的范围限制。
- 模型结束工作流但证据不足：`insufficient_evidence`。
- 旧模型替身/旧报告没有结构化字段：`legacy_unverified`，保留原 Markdown，不自动升级为有证据支持的诊断。

归一化顺序：先检查当前执行所有权；再采用 Runner/工作流当前已发生的权威终止事实（预算、依赖、超时，以原异常或最初终止事件分类，报告生成失败不得覆盖先前预算事实）；随后应用确定性的无告警范围结果；最后才校验正常模型输出。校验或渲染错误不能把前述权威 outcome 改成普通证据不足。重放脚本中的失败同样经此归一化路径。

错误分类先使用已有异常类型，禁止通过任意错误字符串猜测预算类型。预算/超时路径尽可能不再次调用模型，程序生成部分报告；失去执行所有权的 Worker 不得补写任何报告。任务恢复清理上次尝试的终态结果，防止旧结果覆盖新结果。

## 二、存储、接口与前端兼容

在 `DiagnosisReport` 增加 nullable JSON `structured_result`，通过下一条 Alembic 迁移添加，旧行保持 NULL。内存仓储同步支持。由现有 report/complete/error 事件在所有权保护的事务内写入正文和结构化字段。

详情与流式摘要返回可选 `diagnosis_result`；旧 `report/response` 字段保留。report、complete、错误部分报告和终态重建路径都须一致传递该字段。列表保持摘要和分页，不能因此重新加载全部证据。

前端沿用现有安全 Markdown 渲染，只增加诊断结果状态与证据边界说明；断线、刷新、历史读取、缓存与账号切换时保持一致。旧历史显示为“历史报告，未进行结构化校验”。SSE 的传输完成不显示为“根因已确认”。

## 三、可核验案例与评测

新增独立版本化案例目录，首批 12 个合成案例：CPU 负载与死循环对照、内存压力、下游超时、连接池耗尽、错误配置、发布回归、无告警、关键日志缺失、指标日志冲突、旧手册误导、工具依赖失败。允许组合场景，但必须保持 12 个不同可解释案例。

案例拆成两部分：

1. 输入：任务、服务目录片段、带时间/服务/实例的工具响应与证据。
2. 私有评测期望：合成故障原因、可接受结论范围、必要支持引用、禁止无证据下结论的情况、人工复核说明。期望不得进入模型提示词、工具输出或工作流决策。

来源统一标为 `synthetic`；这里的“已知原因”是构造条件，不能声称经外部运维专家标注。每个案例有复核清单，用户以后可记录人工复核者和日期；没有复核的保持 `review_status=unreviewed`。

保留旧关键词门禁；新增结构化契约/引用校验、结果状态匹配、支持/反证覆盖等可重复检查。根因语义、建议合理性仍使用人工评分表，未评分时返回 NULL，不能计零也不能计正确。

评测输出样本数、来源、规则通过数、人工复核覆盖数、每项失败原因；不把程序门禁称为根因准确率。

## 四、固定流程对照与真实工作流运行

提供两种明确隔离的模式：

- `replay`：无模型/云工具调用，使用输入案例和独立的脚本化模型响应，验证控制流、契约、证据引用和展示。模型响应不能读取评测期望。输出明确 `semantic_accuracy_measured=false`，不声称 Agent 胜过 baseline。
- `live`：用户主动选择并配置模型后，在相同合成工具响应上运行真实模型。复用现有 Plan–Execute–Replan 节点，工具注入通过显式运行时依赖入口，不全局覆盖生产单例或凭据。固定流程顺序为目标服务指标、目标服务日志，然后调用同一结构化总结与校验器。

固定流程与 Agent 使用同一任务、服务范围、模型、温度、工具数据、报告 schema、模型额度和评分方式；相同公共种子/运行配置与输入摘要写入产物。Agent 可以基于中间结果选择补充查询，额外查询的成本如实计入，baseline 没有补查能力是对照设计的明确差异。

CLI 默认只运行 replay。live 需要明确命令选项，有每例模型调用上限、总运行上限和取消行为；不自动消耗真实模型额度。至少支持指定 case、重复次数和输出目录。

逐次保存工具轨迹、模型调用次数、已观测 usage 及覆盖率、整体耗时、错误、结构化结果和规则评分。无 usage 保持 NULL；不从脚本次数伪造真实 Token 或金额。

重放模式中的脚本模型调用数与本机耗时单独标注，不作为模型性能。live 未执行时不提供预制的“提升百分比”；即使两方案持平或 baseline 更好也完整保留结果。

## 五、无真实凭据演示

新增独立本地 CLI 演示入口，默认绑定 `127.0.0.1` 的专用端口，不能修改生产服务目录或写入生产数据库。提供案例列表、重放过程、结构化结论、支持与反证、缺失证据和运行模式说明。

仅依赖项目 Python 环境，不要求 DashScope/CLS 密钥或 Docker。入口与案例加载器不能导入 `app.main`、全局向量实例或真实 MCP 初始化。需要将真实 Agent 的依赖获取变成显式、可注入入口；生产默认行为保持不变。

演示服务只开放内置案例 ID，拒绝任意路径和任意 URL，不接收执行代码；显示内容使用 textContent 或现有安全渲染，不直接插入模型/案例 HTML。输出目录只存放合成数据；演示入口默认没有真实处置能力。绑定非回环地址不支持。

README 提供安装、启动、浏览器地址、CLI 对照命令、退出方式和故障案例解释。文档将 replay、合成工具上的真实模型评测、真实业务试用三种证据分开。

## 验收与实施边界

1. 现有创建、持久化、重试、所有权、重连、认证和前端回归继续通过。
2. 结构化字段贯穿图状态、事件、内存/SQL 仓储、详情、重连终态与前端；旧数据无需重跑即可读取。
3. 合法/非法/跨任务/冲突/失败/示例证据引用、无证据和预算/依赖失败均有有意义的回归。
4. 新迁移在独立 PostgreSQL 测试库验证；`alembic check` 无未提交 schema 变化。
5. 12 个案例有完整输入、独立期望和复核清单；明确哪些尚未人工复核。
6. replay 的双方案运行和演示在没有 `.env`、没有云密钥的干净代码副本中通过；测试防止真实供应商/MCP/生产数据库调用。
7. live 注入链路用受控传输替身验证，默认不做付费模型实验。真实效果待用户主动运行，不伪造数字。
8. Python、Node、Ruff、Bandit、安全审计、Compose 校验按改动范围执行，新增逻辑先写失败用例再实现。

实现方可以决定模块拆分、列表/文本的具体上限和演示页细节，但不得弱化现有认证、脱敏、处置与所有权检查。设计确认后再编写详细实施计划；本设计文件本身不授权部署、真实写操作或付费模型评测。
