# RCAEval 公平两阶段诊断设计

## 意图

把当前“固定候选、固定工具调用、多次模型转述”的评测链路改造成可审计的两阶段诊断：
Baseline 与 Agent 共享完全相同的初始证据；Agent 只有在证据不足时才能请求一次有界补查。
本设计同时解决证据截断、候选遗漏、上下游方向误判、故障机理与传播症状混淆，以及评测口径不公平。

这项工作面向本地 RCAEval 录制数据，但证据契约、预算边界和因果约束不得依赖案例编号或答案标签，
以便后续复用于真实本地诊断。

## 目标

- 所有初始证据和补查证据在进入 `ToolMessage` 或模型上下文前完成结构化有界化；不提高全局 16 KiB 工具结果上限。
- Baseline 与 Agent 使用字节完全相同的匿名初始证据包，并记录其哈希以验证公平性。
- 删除“模型选定唯一工具—模型转述工具结果—最终模型重新判断”的无效调用链。
- Agent 最多进行一次结构化补查；无补查时一次模型调用，有补查时最多两次。
- 候选选择兼顾直接资源信号、延迟、拓扑方向和机理多样性，不再等价于异常倍数 Top-3。
- 明确区分直接资源异常、可能传播症状、模糊信号和不可观测机理。
- 为 loss 建立显式机理画像；没有网络丢包相关遥测时必须标记不可观测，不允许从延迟单独反推 loss。
- 服务、故障类型、因果假设和细粒度证据引用保持一致；证据不足时允许安全拒答。
- 分开报告执行成功、候选召回、成功执行条件准确率、端到端准确率、拒答和模型用量。

## 非目标

- 不追求在18例开发集上达到100%，不按案例编号、服务名称或答案标签编写分类分支。
- 不运行或查看剩余36例密封答案来指导实现。
- 不把 16 KiB 安全上限提高到更大值来掩盖结构问题。
- 不在缺少直接证据时把隐藏注入标签包装成确定性生产诊断。
- 本阶段不替换通用生产 LangGraph；新增两阶段协调器作为显式可选路径，生产默认行为保持兼容。

## 反目标

- 不能为了提高 Exact Match 而降低安全拒答标准。
- 不能让 Baseline 获得未压缩原始数据而让 Agent 只看到压缩数据。
- 不能把模型生成的摘要当作原始证据或授权证据。
- 不能在同一次最终盲测前反复查看剩余36例结果并继续调参。

## 约束

- Python 3.13、现有 Pydantic/LangChain/LangGraph/pytest/Ruff 技术栈，不引入新的运行时依赖。
- Ground truth 只在两种策略都完成预测后进入评分代码。
- 初始包、补查包、模型输入、模型调用次数和超时均有确定性上限。
- 所有服务名必须来自当前案例服务目录；所有证据引用必须能回到录制数据。
- 18例从本设计开始是开发/回归集；剩余36例保持未运行、密封，直到用户明确批准最终盲测。
- 实现后的付费模型重跑另行给出调用和 Token 估算，获得确认后才执行。

## 已考虑的方案

### 方案一：保留现有 Agent 图并局部修补

优点是改动小；缺点是固定计划、无效模型转述和双重压缩继续存在，无法证明多步链路产生增益。
未采用。

### 方案二：公平的两阶段诊断管道（采用）

程序生成共享、有界、无标签的初始证据包；Baseline 只基于该包诊断，Agent 可以直接诊断，
也可以请求一次受约束补查后再诊断。它能隔离“证据质量”和“补查价值”，并保留真正有意义的 Agent 行为。

### 方案三：确定性分类器加模型解释

可靠但会把启发式规则变成最终权威，容易过拟合 RCAEval，且不再检验 Agent 的诊断能力。未采用。

## 总体架构

```text
录制遥测
   │
   ▼
确定性特征与拓扑提取
   │
   ▼
共享 InitialEvidenceBundle ───────┬─────► Single-stage Baseline ─► DiagnosisResult
   │                              │
   │                              └─────► Two-stage Agent
   │                                         │
   │                                  直接诊断或 EvidenceRequest
   │                                         │
   └─────────────────────────────── 有界补查（最多一次）
                                             │
                                             ▼
                                      DiagnosisResult

两种结果都完成后 ─► 解封本批答案 ─► 独立评分
```

## 共享证据契约

新增版本化的 `InitialEvidenceBundle`，包含：

- 匿名任务元数据、服务目录、时间窗口和 incident time；
- 候选集合及每个候选的选择原因；
- 有界的 `candidate_pool_hints`：只包含未入选服务的服务名、可见信号类别和拓扑邻接依据，
  不包含根因概率或答案信息，供一次补查在有证据依据时扩展候选；
- CPU、mem、delay、disk、socket、loss 六类 `MechanismProfile`；
- 明确的 `inbound_callers` 与 `outbound_dependencies`，并使用自然语言无歧义说明调用方向；
- 直接资源信号、可能传播症状、模糊信号、不可用信号四类解释；
- 有界趋势、Trace、日志摘要和数据缺口；
- 每个可引用事实的稳定 `evidence_ref`；
- `omitted_paths`、采样方法和局限性；
- 包体版本、UTF-8 字节数和内容哈希。

候选在选出后按稳定服务名排序，而不是按异常强度排序，避免位置等同于根因概率。
异常强度可以保留为事实，但不得命名为 root score 或 probability。

证据构建器必须在返回工具结果前保证序列化内容低于配置上限，并为 ToolMessage/JSON 包装预留空间。
压缩按语义优先级进行：身份与引用、直接机理画像、拓扑方向、关键趋势、Trace、日志摘录。
低优先级字段不足时显式省略；不能返回可被当作成功证据的截断预览。

## 候选选择

候选生成不读取答案，最大候选数保持有界。它从以下来源形成候选池：

1. 每种可用直接资源机理的最强服务；
2. 延迟异常服务，但延迟只作为症状候选而非直接根因标签；
3. 被多个异常调用者依赖、同时具有直接资源信号的下游服务；
4. 拓扑不可用时的全局异常候选；
5. 机理多样性补位，避免公共 diskio 噪声占满候选名额。

最终候选数量由字节预算决定，目标上限为5。选择结果必须记录 `selection_reasons`，
评分阶段报告真实根因是否进入候选，但诊断阶段不可访问该信息。

Agent 的补查默认针对初始候选；也可选择至多一个初始候选外服务，但该服务必须同时位于服务目录和
`candidate_pool_hints`，请求必须引用触发扩展的信号或拓扑依据。合法补查后的服务加入扩展候选集，
评分分别记录初始候选召回和补查后候选召回。不能无依据逐个扫描完整服务目录。

## 机理和传播语义

每个机制画像使用统一状态：

- `direct_signal`：存在与该机理直接相关、超过稳健阈值的变化；
- `possible_symptom`：变化明显，但存在更直接资源异常或拓扑传播解释；
- `ambiguous`：多个机理并存，现有观测不能排除竞争解释；
- `unavailable`：缺少该机理的可用遥测。

delay 在同服务存在直接 CPU/mem/disk/socket/loss 信号时默认是 `possible_symptom`，除非补查提供反证。
调用边固定表达为 `caller -> callee`；下游 callee 的直接异常可以传播到 caller，反向解释必须被一致性门禁拒绝。

同一服务出现多个 `direct_signal` 时，强度比值不能跨单位直接比较，也不能仅凭最大倍数选出故障类型。
只有以下证据可以把某一机理从竞争集合中确定出来：它比其他机理至少提前一个完整采样桶出现并持续，
或者其他机理被证明是跨多数同类服务的 common-mode 信号而该机理是候选服务特有信号。
不满足时，各机理仍保留 `direct_signal` 事实，但总体判别标记为 `ambiguous`，最终 fault 应为 `unknown`。

当同服务已有直接资源信号时，delay 只有在补查同时证明以下条件后才能升级为直接故障：

1. 现有资源信号全部被判为 common-mode，或至少晚一个完整采样桶出现；
2. 延迟在该服务先于其调用者出现并持续；
3. 没有下游 callee 的更早直接异常可以解释传播。

缺少任一项时，delay 保持 `possible_symptom`。

loss 的 `direct_signal` 只从明确的结构化网络指标或可信 Trace 状态字段建立，例如 loss、drop、
retransmit、network error 计数。普通业务延迟、CPU 变化和原始日志文本不能单独支持 loss。
脱敏后的重复日志错误只能作为 `ambiguous` 补充观察，不能把 loss 从 `unavailable` 升级为
`direct_signal`。RCAEval 没有结构化网络证据时，结果必须是 `unavailable`。

## 两种策略

### Single-stage Baseline

- 接收共享初始证据包的原始序列化内容；
- 使用与 Agent 最终诊断相同的诊断约束和 `DiagnosisResult`；
- 不允许请求补查；
- 一次模型调用；
- 无法区分机理时输出 `unknown`，而不是猜测隐藏注入标签。

### Two-stage Agent

第一次模型调用返回二选一的结构化结果：

- 完整 `DiagnosisResult`；或
- `EvidenceRequest`，只能指定目录内1至2个候选服务、允许的机理类别和一种补查视图。

允许的补查视图为有界的候选趋势、候选日志、候选 Trace/调用关系或指定机理细节。
请求不能包含自由路径、任意查询语言、答案字段或目录外服务。协调器验证请求，执行一次补查，
生成 `FollowupEvidenceBundle` 后进行第二次且最后一次模型调用。

第二次调用不能再次请求证据。无效请求、依赖失败或预算不足返回结构化的
`insufficient_evidence`/`dependency_failed`，不得使用不完整预览继续诊断。

如果第一次调用选择直接诊断，但结果未通过一致性门禁，协调器不得事后自动替模型生成补查请求，
也不得用第二次调用修饰同一份无效结论；结果直接降级为 `insufficient_evidence`。模型只有在第一次
调用明确返回合法 `EvidenceRequest` 时才获得第二次调用，这保证“最多两次”的语义可审计。

## 一致性门禁

- 根因服务必须来自初始候选集合，或来自 `candidate_pool_hints` 且经过合法补查加入的扩展候选；
- 顶层 fault 必须由同一根因服务的匹配机理证据引用支持；
- delay 被标记为传播症状时，不能在没有反证的情况下作为最终直接故障机理；
- caller 不能仅因依赖的 callee 异常而被解释为导致 callee 异常；
- 多个直接机理无法区分时，允许服务命中但 fault=`unknown`；
- 所有假设、候选比较和顶层结论必须引用细粒度有效证据；
- 规范化器只拒绝或降级无证结论，不根据答案替模型改写结论。

## 评测与可观测性

每次运行保存：

- 初始证据包哈希和字节数；
- 两策略的哈希一致性；
- 候选数量、候选召回（仅评分后计算）；
- 是否补查、补查请求和补查包大小；
- 执行成功、端到端服务/故障/联合准确率；
- 成功执行条件下的服务/故障/联合准确率；
- `unknown`/拒答率，以及“安全拒答但隐藏标签不命中”的单独计数；
- 模型调用、Token、耗时、超时和预算耗尽。

历史 `baseline` 指标保留为旧版本记录；新结果必须标注评分和证据协议版本，不能直接混为同一实验。

## 错误处理与安全

- 包体无法在最低契约下放入预算时返回明确的 `evidence_budget_error`，不返回授权性预览。
- Provider 错误、超时、无效结构输出和补查失败分别记录，不合并成模型判断错误。
- 日志继续经过敏感信息脱敏；原始日志不得因为补查而绕过现有安全边界。
- Ground truth 文件路径不进入协调器、提示词、证据包或模型 trace。
- 共享包必须不可变；策略不得原地修改后影响另一策略。

## 测试与验收

### P0：可靠性和公平性

- 18例及完整54例的初始包均能离线构建，并通过实际 `sanitize_tool_message` 边界，不产生 `tool_result_truncated`。
- 同一案例两策略的初始包字节和哈希完全一致。
- Agent 无补查时1次模型调用，有补查时最多2次；不存在被丢弃的中间模型摘要。
- 所有错误类型可区分，执行成功率作为独立指标。

### P1：候选和因果语义

- 合成拓扑测试验证 `caller -> callee` 传播方向，不允许反向因果解释。
- 开发集 `case-032` 的证据契约明确显示 productcatalogservice 是 recommendationservice 的下游依赖，
  且前者存在直接资源信号、后者主要是延迟症状。
- 开发集 `case-041` 的候选池包含 ts-train-service，证明公共 diskio 噪声不会占满候选。
- 开发集 `case-054` 将 CPU 标为直接信号、delay 标为可能症状。
- 候选召回、条件准确率和端到端准确率在报告中分开呈现。

### P2：机理可辨识性和诚实拒答

- 合成 loss 指标能够产生 loss `direct_signal`；没有 loss 遥测时返回 `unavailable`。
- socket/disk/mem 等机理不可辨识时允许 `unknown`，且评分报告区分安全拒答和执行失败。
- Exact Match 不再作为唯一质量指标；引用有效性、候选召回和拒答校准同时报告。

### 工程门禁

- 每个行为变更先有失败测试，再实现最小代码使其通过；
- 相关测试、全量 pytest、Ruff 和 `git diff --check` 全部通过；
- 18例先进行无模型离线验证和证据审计；
- 付费重跑前给出预计调用和 Token，并等待用户确认；
- 剩余36例仅在开发集冻结、用户明确批准后运行一次最终盲测。

## 风险和权衡

- 候选上限从3扩展到最多5会增加包体压力，因此必须依赖细粒度证据和语义优先压缩。
- 更严格的机理门禁可能提高 `unknown`，但这比没有证据时猜测更符合生产安全。
- Agent 只有一次补查，无法覆盖所有复杂调查；这是为了控制成本并保证实验可解释。
- 18例已成为开发集，改进后的成绩只能作为回归指标，不能再宣称独立盲测泛化性能。
- 新旧 Baseline 协议不同，历史数值只能作为背景，不能作为严格前后对照。

## 留给实施者的决定

- Pydantic 模型按现有模块边界拆分的具体文件名；
- 稳定证据引用的哈希算法和可读前缀；
- 在满足语义优先级与字节预算前提下，各低优先字段的具体采样数量；
- 测试夹具的组织方式和内部辅助函数命名。
