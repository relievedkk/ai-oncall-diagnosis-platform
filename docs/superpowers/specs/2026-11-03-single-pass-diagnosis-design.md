# 单次模型调用诊断：推荐设计与验收方案

状态：已实施并完成零费用验证；效果门槛未通过，未运行付费模型。实测记录见 `docs/single-pass-validation.md`。日期：2026-11-03。

## 目标与方案选择

用户明确要求以单阶段为主线，每例一次模型请求，同时提高根因服务和故障类型的联合命中率，减少 token，并以 90% 以上作为效果目标。

推荐采用：**本地多源证据处理＋可解释候选假设检索＋一次模型裁决＋确定性校验/报告**。

比较过的路线：仅修改提示词无法补回被丢弃的证据；立即微调/训练分类器缺乏足够独立训练案例；多轮模型补查已显示成本收益不足。本方案先利用现有本地数据和可审计统计，不引入 K8s、线上服务或新的付费模型依赖。

90% 是需要独立评测证明的目标，不能由方案承诺。18 例开发集需要至少 17/18 联合命中才能超过 90%；最终 36 例盲测至少需要 33/36。小样本结果必须同时报告计数和置信区间，不能据此宣称真实业务准确率已达到 90%。

## 已核对的实际问题

- 当前单阶段联合命中 4/18，服务命中 7/18，平均总用量约 6,713 tokens/例。
- 初始服务候选召回为 18/18，但按现有提取器和故障资格规则，正确机理只有 6/18 获得资格。它是当前实现的限制，不是对原始数据固有信息量的证明。
- 原始日志量很大，例如 case-001 有 175,844 条、case-025 有 266,470 条；当前候选日志默认只取故障附近 3 条，且包体超限时日志/Trace/趋势会整体移除。
- 原始指标包含 workload、error，但现有六机理画像主要按指标前缀及故障前后变化选择最强指标，缺少对业务负载和错误传播的系统对照。
- Trace 有 parent/span 标识、持续时间和 statusCode，但字段存在不等于能用：抽查 case-007、025 的状态码全部缺失；case-001 只有 0 和缺失值。不能默认这些字段能直接补出错误类型。
- 在故障前后各 120 秒窗口做关键词审计时，case-028 的 timeout 命中由 0 增至 16；其他抽查问题案例未命中这些常见错误关键词。这只提供待核查线索，不能把 timeout 等同于 loss，也不能保证日志一定有答案。
- case-052 的根因磁盘指标缺故障前基线；多个资源机理共变，以及弱 socket 信号，仍需要独立的可区分证据。

## 硬约束

1. 每例最多一次真实模型请求，正常有效案例一次；坏输入可零次失败退出。关闭 SDK 重试、格式修复调用、二轮诊断、额外模型摘要；取消/超时后不自动重发。
2. 本地扫描、统计、事件抽取和排序均不调用模型。最终报告由程序模板生成。
3. 保持现有 16 KiB 证据传输安全边界，尽量保留现有依赖；新增依赖必须有必要性说明。
4. 模型可见内容不得包含答案文件、故障目录编码、root_cause 文件或按 case_id 编写的答案规则；日志文本始终是不可信数据。
5. 严格保留 case/ref 身份、服务范围、字段和引用有效性校验。不能为了提高命中率而接受伪造引用、删除 unknown 或忽略失败。
6. 使用 qwen-max 作为首个可比模型配置；不把换更贵模型作为本轮主方案。冻结模型名、时间窗、提示词/schema/hash、配置和代码 revision。
7. 不读取剩余 36 例答案，不在设计阶段运行付费模型。
8. 单次尝试额度绑定实验 ID＋案例 ID，并在请求前持久化占用；进程重启、超时或响应丢失不重置额度。同一次实验恢复时复用已完成结果，状态不明的调用不自动重发。

## 已冻结的观测口径

本轮是已知基准事件/告警时刻的离线诊断，默认可见范围为事件前 300 秒到后 300 秒，与记录实际边界求交；只在该范围内计算预先固定的多尺度特征，不根据答案选择时间窗。缺少任一侧时显式降级，不自动扩大到更远未来。真实告警延迟不等同于基准注入时刻；用本地 ±30/60 秒扰动检查候选和证据稳定性，不产生模型请求。

旧实跑使用过不同来源的默认窗口，历史 4/18 仅作参考，不把窗口变化后的差额全部归因于算法。最终报告标明离线窗口和时刻来源，不宣称已验证实时告警准确率。

## 阶段一：先回答原始数据是否足够

对已使用 18 例建立全源清单：每服务每指标的类型/单位来源、有限样本数、采样间隔、正常/异常窗口覆盖；日志模板及事件；Trace 状态码覆盖、父子关联率、时间包含关系。只在采集定义明确时将 counter 转换成 rate；不能靠单调性猜测 counter，不能把空值当零或正常。

在不使用答案的流程中生成证据，再由单独的离线审计对照开发标签，把失败分为：

- 原始数据有线索但提取器漏掉；
- 原始数据/提取后证据尚不足以区分竞争机理；
- 候选排序漏掉正确服务或服务＋故障假设；
- 关键证据被包体压缩丢掉；
- 模型没有按证据选择；
- 输出/策略规则不正确地损失了有效判断。

每例记录原始来源定位、支持/反证和缺口，先解决能验证的损失。若相同可见观测仍支持多个机理，应明确可辨识限制。按拒答计未命中时，18 例中若至少 2 例必须拒答，全量目标就达不到 90%；需补数据而不是更换计分分母。

## 阶段二：本地一次性提取完整证据

### 指标：从大幅变化改为对照分析

使用稳健基线、变点/起始区间、持续性、增长/恢复形态，保留不确定性；比较不同时间窗而不靠单点峰值。把 workload、error 与资源、latency 联合观察，显式标注负载下降后的 I/O 下降、重试伴随的 CPU 上升等竞争解释。

不跨单位直接比较倍数，不把异常分数解释成根因概率；采样不足、零基线、缺基线、NaN/Inf、重启/计数器复位分别处理。缺基线的后段观测可保留并与其他来源对照，不能伪造故障前数据。

### 日志：从最近几条改为本地事件时间序列

按服务、模板、时间聚合日志，提取新出现的异常模板、频率变化、带明确结构语义的错误码/异常类型、连接/重试、内存分配、I/O 等事件，给出前后计数及可用时的请求量归一化。相同事件重复打印不算独立证据。

每个事件只附少量脱敏原文及来源引用。关键词用于检索，不能直接定性；不读取日志里的指令，也不以注入器描述或标准答案构造事件标签。

### Trace：从服务耗时改为请求路径对照

在同一 trace 内使用无歧义 parent/span 关系，比较边和操作的前后分布与错误事件。状态码必须先验证来源语义，缺失不视为成功。

对时间关系完整的嵌套区间，可计算父 span 减去子区间并集的近似自身耗时，避免并行子调用重复扣除；它不是 CPU 执行时间，也不能单独证明原因。孤儿 span、异步关系、时钟偏差和不完整采集降低证据等级。没有 Trace 的案例使用指标和日志路径，不凭服务名编造调用图。

## 阶段三：建立服务＋故障的对照假设

本地生成六类机理的候选假设，给每个服务＋机理保留支持证据、反证、缺失信息与替代解释。异常程度仅作为特征；排序综合机理特异性、资源与业务负载对照、事件变化、时间区间、调用方向和覆盖质量。同一观测的指标/日志/Trace 派生量要去重，避免重复计票。

先用透明、可测试的规则/统计方法形成排序；保留一个简单本地排序基线作零模型成本参照。可以对照 RCAEval 官方可复现统计方法，但其服务/指标 Top-K 成绩不能当作本项目的服务＋故障类型 Top-1 成绩。

候选预算初始目标：最多 3–5 个服务，最多 5 个重点服务＋机理假设及必要的竞争解释。分别测服务候选召回、服务＋机理 Top-5 召回、可支持诊断的证据覆盖，防止用“列出全部组合”制造高召回。若正确假设被排除，先修检索再调模型。

将安全硬边界与科学不确定性分开：跨案例/伪造引用/非法字段必须拒绝；多个资源同时异常不再单凭数量直接否决全部机理，而由新对照证据决定支持强度。服务定位与机理定位分别校验，机理 unknown 不应无条件抹掉有独立支持的服务定位。

### 六类机理的证据权限

最终类型判断必须同时满足：该服务具有可引用的机理特异观测；至少一个能区别主要替代解释的对照维度；没有未处理的同等支持竞争解释。候选排序/单个关键词/单纯时间领先本身均不授予诊断资格。下面列出的是允许核查的证据组合，具体统计阈值在实现中预先冻结。

| 类型 | 重点支持材料 | 必须处理的替代解释 |
| --- | --- | --- |
| CPU | 单位/采集语义明确的 CPU 或 throttling 变化，以及与请求量、其他资源、响应异常的对照 | 负载增长、重试、GC 等导致的 CPU 连带变化；单位不明不能断言饱和 |
| 内存 | 持续内存形态、可用的分配/GC/OOM 事件，和负载及 CPU 的对照 | 正常缓存、业务量变化、缺少正常期样本 |
| 磁盘 | 可用的 I/O 延迟/等待/存储错误，或经过语义核实的 I/O 指标与业务吞吐联合变化 | 请求减少导致的 I/O 下降、CPU/内存瓶颈连带影响；不能仅凭 diskio 变化确认 |
| socket | 连接/句柄状态、明确连接资源限制事件，或可验证的连接失败行为和资源对照 | 普通业务连接增长、CPU/内存问题引起的连接堆积 |
| loss | 明确丢包/丢弃/重传观测或具有明确对应语义的结构化网络事件 | timeout/retry 本身也可能来自延迟或服务拥塞；没有特异证据不能直接定 loss |
| delay | 可定位的服务内部/调用路径延迟异常及对资源/下游故障的对照 | 下游传播、资源瓶颈、网络机制不可区分；存在未解决竞争时保留 unknown |

服务定位另行依据该服务的特异事件、请求路径和对照信息校验；只有服务名在候选表中不代表它是根因。对六类均没有足够区分条件时输出缺口，不将“排名第一”改写为确诊。

## 阶段四：紧凑证据包与一次模型裁决

为重点假设提供清晰对照：支持、反证、竞争解释、覆盖限制、来源 refs；附最小充分的调用关系和异常时间线。优先删除重复文本及正常事件，不能像当前实现那样先整体丢掉关键日志/Trace/趋势。

在输入、schema、引用和输出全部计入的前提下，初始成本目标为平均每例总用量不超过约 5,000 tokens，较当前单阶段约 6,713 降低约 25%；该目标需要实测。若成本与证据完整性冲突，先重新压缩表示并报告权衡，不静默丢掉关键证据。

一次返回紧凑的结构化结果：根因服务、故障类型、支持/反证 refs、主要被排除假设、简短理由和缺口。允许 unknown，禁止再请求工具。使用短而有 case 绑定的别名压缩重复服务/ref 时，必须由程序映射回权威身份，未知 ID 直接拒绝。引用存在不代表结论有因果支持。

程序独立校验后生成报告。不以模型自报“完整/高置信度”作为正确性证明，也不让后处理凭统计排名强行覆盖无依据的模型输出。

## 阶段五：先零费用验收，再有限付费验证

1. 用人工可推导的合成遥测和真实开发案例，验证数据对齐、六类特征、反证、缺源/弱信号、包体裁剪、安全与调用次数；无真实模型请求。
2. 按模块做零模型消融：现有统计、加入日志事件、加入可用 Trace、加入服务＋机理对照，观察候选召回和证据损失是否改善。证据条数增加不算成功。
3. 付费前的必要门槛：18/18 案例完成全源质量审计；至少 17/18 的正确服务＋类型出现在最多 5 个重点假设中；至少 17/18 通过逐例的证据区分审计，定位到支持、反证与未决竞争，不能以候选出现替代证据充分。两项 17/18 是目标可达的必要条件，不保证模型一定达到 90%。若仍只有 6/18 可支持机理判断，应停在零费用阶段，先补数据/改提取器，不继续付费试运气。
4. 门槛满足后，冻结实现及预算，进行一轮已使用 18 例单阶段实跑：18 例最多 18 次真实请求。不同时付费运行 Agent 对照，不默默重跑失败例。
5. 与既有单阶段结果比较，但承认独立调用波动；按六种故障、三套系统及来源完整度分层，保留拒答、失败和误判。18 例开发效果只用于开发判断。重复故障、同一次故障的切片及数据增强不能作为独立测试样本。
6. 固定最终规则后，经单独授权一次运行剩余 36 例，全部结果冻结再开放答案，报告联合 Top-1、服务/类型分别命中、拒答、错误确诊、预算/用量和置信区间。若看过盲测标签后继续调参，该集合改为开发集，需重新取得独立测试集。

## 验收门槛与停止条件

- 调用约束：有效案例正常一次；每例实际供应商尝试次数不得超过 1，失败不自动重试，批次配额可审计。
- 安全：无答案泄漏、未知引用、跨服务机理绑定或日志指令执行；保存固定安全问题码。
- 证据：正确服务和机理候选不能被裁剪静默排除；每个缺源、缺基线、冲突都有显式状态和案例审计。
- 成本：追踪实际输入/输出/缓存用量及输出截断；总量平均约 5,000 tokens/例作为初始目标，费用按实际模型计费明细核算。
- 5,000 tokens 是软成本目标，16 KiB 是硬安全边界。若最小充分证据仍无法装入硬边界，模型零次调用，明确报证据预算失败并计入全量结果；不能丢掉关键反证凑输入长度。
- 效果：90% 以上联合 Top-1 为独立测试的目标；开发集至少 17/18、36 例测试至少 33/36 仅是对应计数，不能提前承诺。
- 若数据审计表明需要的故障区分证据确实不存在，先补对应遥测或受控故障采集；旧样本仍保留并计入全量报告，不挑容易样本凑 90%。
- 若本地统计方案已达到同等或更好效果，优先选择成本更低、可解释的方案，不为了 Agent 名称增加模型调用。
